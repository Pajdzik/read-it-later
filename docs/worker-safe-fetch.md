# Historical: safe article fetch boundary trial

This document records a superseded `ARTICLE_FETCHER` gateway design and its Worker socket experiments. The current app uses the `ARTICLE_EXTRACTOR` service in `capture/`; see [Cloudflare capture](cloudflare-capture.md), [URL Markdown capture](url-markdown-capture.md), and the [deployment guide](deployment.md). The trial evidence below is historical and does not describe current Wrangler configuration or verify the live deployment.

## Implementation boundary

The application Worker keeps the queue, leases, title rules, redirect policy, HTML validation, metadata, and Defuddle conversion. Its existing `ARTICLE_FETCHER` GET interface is retained. The private gateway Worker accepts only that GET request, validates the target, and passes the original URL in a fixed versioned JSON message to one Container instance. The Container makes a single upstream request and returns status, a short header allowlist, and bounded raw bytes, or a stable typed error. Protocol v2 requires an internal version marker, discards upstream internal headers, and fails closed on version mismatch. The Worker validates the response and rebuilds it locally so the Container's internal URL does not appear as the response URL. Metadata and Defuddle share one initial inert HTML document.

The Container validates each CNAME alias and every returned A/AAAA address with `ipaddr.js`, rejects an answer set containing any private, reserved, documentation, transition, or otherwise non-global address, and chooses one approved numeric address. It creates a fresh Node HTTP/TLS request with `agent: false`; the socket hostname is numeric, while the HTTP `Host`, TLS SNI, and certificate identity check use the original URL host. Certificate verification stays enabled. It sends only fixed `Accept`, `User-Agent`, `Accept-Encoding: identity`, and `Connection` headers. It does not follow redirects, decompress compressed content, forward cookies or credentials, or log source URLs or content.

The gateway caps the original URL at 8 KiB, the JSON request at 12 KiB, upstream response headers at 16 KiB, and the HTML body at 2 MiB. It serves one active outbound fetch at a time. Container startup has a separate ten-second readiness allowance, followed by a five-second network/response budget. The application Worker allows up to fifteen seconds for the first hop, five seconds for subsequent hops, and twenty seconds total for fetching; readiness cannot extend that total. Cancellation prevents a late startup result from fetching an article. The three-redirect limit, HTTPS-downgrade block, UTF-8/HTML validation, and 256 KiB Markdown output cap remain enforced.

The Container explicitly uses direct outbound internet and disables Cloudflare HTTPS interception. The code relies on the numeric socket connection and Node's normal trusted root store; adding an outbound proxy, `ContainerProxy`, HTTPS interception, a proxy environment variable, or an extra CA would invalidate the tested pinning assumptions. Cloudflare documents that outbound HTTPS is not intercepted by default and that interception injects a runtime CA ([outbound traffic](https://developers.cloudflare.com/containers/configuration/outbound-traffic/)).

The gateway Worker has no `workers.dev` hostname or preview URL and no public route. It becomes callable only when an operator deploys the app with a service binding. The [manual capture stack workflow](../.github/workflows/deploy-capture-stack.yml) deploys one selected environment and generates the binding for that deployment only; it leaves capture disabled and never runs on pushes. The workflow has not been run. Logs omit invocation URLs and trace sampling is set to zero to avoid retaining article URLs in platform telemetry.

Cloudflare Containers are available on the Workers Paid plan, not Workers Free. The plan starts at $5/month and includes monthly Container CPU, memory, and disk allowances; additional active resource use and network egress can be billed. See Cloudflare's [Container pricing](https://developers.cloudflare.com/containers/platform/pricing/) and [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/). This code and its CI checks do not change the account plan, deploy the gateway, or activate capture. A plan change and deployment require separate operator action.

The [Paid Worker extraction trial](worker-extraction-benchmark.md#paid-plan-trial-october-25-2026-utc) passed all 70 fixture requests with complete CPU telemetry; the maximum observed CPU was 5,641 ms against a 30,000 ms budget. The remaining release gate is deployed staging verification: deploy the gateway through the manual workflow, bind only staging, verify real Container egress and TLS behavior against representative public hosts, exercise application redirect and retry handling and scheduled capture, and review resource use before enabling production capture. A successful local TLS fixture test proves Node's SNI and certificate validation logic, not Cloudflare's remote Container networking behavior. Keep production disabled until those checks pass.

## Deployed edge trial

A fixed-target Worker ran three requests against one public GitHub endpoint. It connected to the pinned address on port 443, used `startTls()` with the requested hostname, and required an HTTP response. A hostname connection to `github.com` was the TLS control; the HTTP control connected to the same pinned address on port 80. The recorded outputs are in [edge-results.json](../probes/edge-pinned-fetch/edge-results.json).

Each run returned `malformed_or_empty_response` for both the pinned-IP case with expected hostname `github.com` and the pinned-IP case with deliberately mismatched hostname `invalid.example`. Each hostname TLS control returned `tls_http_response`, and each pinned HTTP/80 control returned `http_status_301`.

The controls show that the Worker could reach this GitHub host by hostname over TLS and reach the fixed IP over raw HTTP. The pinned TLS cases produced no complete HTTP status, so the trial does not establish whether the runtime accepted or rejected either certificate hostname. It does not demonstrate wrong-host acceptance. It also does not test all Cloudflare locations, redirects, DNS rebinding, mixed A/AAAA answers, private/reserved destinations, or other public origins.

## Worker runtime API evidence

The `cloudflare:sockets` type declaration includes `TlsOptions.expectedServerHostname`, but the current [workerd socket implementation](https://github.com/cloudflare/workerd/blob/main/src/workerd/api/sockets.c++#L865-L875) guards that option as unsupported: depending on the runtime gate it rejects the option or logs that it is unsupported. A related [workerd issue](https://github.com/cloudflare/workerd/issues/6903) reports production behavior where the option is ignored. The fixed-target trial is consistent with pinned TLS being unusable in the tested Worker, but it does not identify the exact failure stage.

Cloudflare's [TCP sockets documentation](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/#considerations) says outbound sockets to Cloudflare-owned IP ranges are blocked and recommends `fetch()` for HTTP-based services on ports 80 and 443. That recommendation is not a blanket prohibition on raw HTTP sockets at those ports: the port-80 control here returned 301. A direct socket approach also has a target-coverage limitation because some public sites use Cloudflare-owned destination IPs.

The [Workers `node:https` documentation](https://developers.cloudflare.com/workers/runtime-apis/nodejs/https/) says its client methods wrap global `fetch()` and do not provide the underlying socket. It lists TLS options such as `servername` and `rejectUnauthorized` as unsupported, so it does not provide a way to pin a destination while preserving the URL hostname for TLS identity checks.

## Platform-managed public egress and explicit pinning

There is a separate, potentially viable boundary: Cloudflare documents that hosted Worker outbound HTTP goes through a local proxy that checks whether a request targets the public Internet or the Worker's own zone origin, rather than internal services ([Workers security model](https://developers.cloudflare.com/workers/reference/security-model/#api-design)). In the open-source [workerd configuration](https://github.com/cloudflare/workerd/blob/main/src/workerd/server/workerd.capnp), the implicit `internet` service backs global `fetch()` and defaults to `network.allow = ["public"]`; the network policy documentation says it filters resolved hostname addresses against that allow/deny policy before a connection is made.

That is a platform-enforced public-address policy, not application-controlled DNS pinning. It may be an acceptable way to meet the public-egress requirement if the owner accepts Cloudflare's policy as the enforcement boundary and deployed tests confirm its behavior for this app. Cloudflare's security model includes an exception for the Worker's own zone origin. The current app rejects its configured `APP_ORIGIN`, but it has not tested the full same-zone origin exception or a controlled rebinding case. The fixed raw-socket trial above does not test global `fetch()` policy.

Before using this alternative, agree that a platform-managed public-egress allowlist satisfies the desired guarantee, then verify the deployed Worker rejects controlled non-public and rebinding destinations, preserves TLS hostname verification, follows only manually validated redirects, and cannot reach its own zone origin through another hostname. Keep the Worker free of private service bindings during that evaluation. If explicit app-level address pinning remains required, this Worker-native `startTls()` path is not demonstrated to support it; use a controlled gateway or another separately approved runtime.
